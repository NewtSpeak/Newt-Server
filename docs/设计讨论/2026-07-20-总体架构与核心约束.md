## 1. 产品目标（本轮共识）

设计一套 **语音 + 多频道** 的即时协作/社区系统，能力对标 Discord / KOOK：

- 用户可创建/加入多个互相独立的 **「服务器」（Guild）**
- 每个服务器下可有多类 **子频道**：至少包含 **文本频道**、**语音频道**
- 服务器级与频道级均支持 **完整 RBAC 权限控制**
- 语音走 **SFU**，控制面与媒体面 **物理/工程上拆成两个项目**

---

## 2. 项目拆分（已定方向）

### 2.1 原则

**服务端（控制面）与音频 SFU 节点（媒体面）必须作为两个独立项目创建与演进。**

| 项目 | 职责边界 | 不负责 |
|------|----------|--------|
| **Owl-Server** | 用户与身份、服务器/频道/成员、RBAC、消息与状态、会话编排、节点注册与鉴权、向客户端下发「去哪个 SFU / 用什么 token」 | 不转发 RTP/媒体载荷；不长期持有大规模媒体状态 |
| **Owl-SFU** | WebRTC 入会、音视频轨道转发（SFU）、房间内订阅/发布、节点容量与健康、与 Server 的控制通道 | 不做业务 RBAC 权威源；不存历史聊天；不替代账号体系 |

### 2.2 拆分收益

1. **独立扩缩容**：语音高峰只加 SFU 节点；聊天/权限高峰只扩控制面。
2. **故障隔离**：SFU 异常不拖垮消息与权限服务；控制面抖动不应直接撕裂媒体（需会话续约策略，后续定）。
3. **安全边界清晰**：媒体节点权限极小；业务权限只在 Server 裁决。
4. **部署灵活**：SFU 可贴近用户或内网机房；Server 可中心化。

### 2.3 仓库与命名（建议）

| 仓库 | 建议名 | 说明 |
|------|--------|------|
| 控制面 | `Owl-Server`（当前） | 本仓库 |
| 媒体面 | `Owl-SFU`（待创建） | 独立 Git 仓库，独立版本与发布节奏 |

API / 协议文档可放在 Server 的 `docs/`，或后续抽 `Owl-Protocol`；首期 **协议草案放在本目录或 `docs/协议`** 即可。

## 3. SFU 节点容量目标

### 3.1 目标

- **单 SFU 节点目标负载：约 1000 并发用户**（以「已连接并占用媒体资源的语音用户」为口径，精确定义见待决）
- 设计时必须同步考虑：
  - **出站/入站带宽**
  - **内存与 CPU**（编解码策略、包转发路径、并发连接）

### 3.2 容量模型（粗算，用于架构约束，非压测结论）

语音以 **Opus ~32–64 kbps 上行**、SFU **选择性转发** 为典型场景（非 MCU 混流）：

| 场景 | 粗算要点 | 对节点含义 |
|------|----------|------------|
| 1000 人同房间全订所有人 | 下行带宽近似 \(N\times(N-1)\times bitrate\)，不可行 | **禁止**默认「全员全订」；必须按频道/订阅关系裁剪 |
| 1000 人分散在多个语音频道 | 每个语音频道内人数有限，节点总连接数 1000 | **按频道隔离房间**，容量按「连接数 + 活跃轨道数 + 订阅边数」计 |
| 大频道（如 50–100 人同频） | 订阅边数上升，带宽与 CPU 主要瓶颈 | 需限流、可选降码率、发言者优先订阅等策略（后续） |

**架构约束（本轮写入）：**

1. SFU **只做转发**，不做全员混流 MCU（除非后续单独「直播/舞台」模式）。
2. 媒体房间粒度建议对齐 **语音子频道**（一个语音频道 ≈ 一个 SFU room，或可映射）。
3. 单节点 1000 人指 **节点级并发**，不是「单频道 1000 人默认全订」；单频道上限与订阅策略需另立指标。
4. 节点上报 **可用容量**（连接数、带宽、CPU、内存），由 Server **调度进房**，避免打满单点。

### 3.3 资源预算（设计阶段检查清单）

实现/选型前应用压测填实，此处先列必须度量的项：

| 资源 | 关注点 |
|------|--------|
| 带宽 | 单用户上下行峰值、节点总出口、公网/内网差异 |
| 内存 | 每 PeerConnection / 每 track 开销、抖动缓冲、包队列 |
| CPU | 纯转发 vs 转码（默认 **避免服务端转码**）、SCTP/DTLS 开销 |
| 连接 | UDP/ICE 并发、文件描述符、NAT 穿越失败率 |

**初步原则：默认不转码、不混流；优先转发 + 客户端侧处理。**

## 4. 领域模型与 RBAC

### 4.1 核心实体（逻辑）

```
平台用户 (User)
    │
    ├── 成员关系 (Member) ──► 服务器 (Guild / Server)
    │                              │
    │                              ├── 角色 (Role) + 权限集
    │                              ├── 成员角色绑定
    │                              └── 子频道 (Channel)
    │                                       ├── 文本频道
    │                                       ├── 语音频道
    │                                       └── （可扩展：公告/舞台等）
    │                                            │
    │                                            └── 频道级权限覆盖 (Overwrite)
    │
    └── （全局：平台级角色/封禁等，后续）
```

说明：

- 用户可加入 **多个互相独立** 的服务器；服务器之间 **数据与权限不共享**（除非显式跨服能力，首期不做）。
- **服务器** 与 **其下每个子频道** 都要支持从 RBAC 体系完整控制。

### 4.2 RBAC 设计方向（对标 Discord 风格，可落地）

采用 **「角色权限 + 频道覆盖」**，而不是为每个用户单独维护全量 ACL 表（可扩展为用户级覆盖，但默认走角色）。

| 层级 | 作用 |
|------|------|
| **服务器默认权限** | 角色在服务器上的权限位（如管理频道、踢人、发消息、连麦等） |
| **频道权限覆盖 (Overwrite)** | 针对某频道，对「角色」或「成员」允许/拒绝特定权限 |
| **计算顺序（建议）** | 基线角色并集 → 应用拒绝覆盖 → 应用允许覆盖 → 管理员/所有者短路（细节待定稿） |

**权限位示例（草案，非最终列表）：**

**服务器级**

- `GUILD_ADMIN` / `MANAGE_GUILD`
- `MANAGE_ROLES` / `MANAGE_CHANNELS` / `KICK` / `BAN`
- `CREATE_INVITE`
- …

**文本频道**

- `VIEW_CHANNEL` / `SEND_MESSAGES` / `MANAGE_MESSAGES` / `ATTACH_FILES` / …

**语音频道**

- `VIEW_CHANNEL` / `CONNECT` / `SPEAK` / `MUTE_MEMBERS` / `MOVE_MEMBERS` / `STREAM`（若支持） / …

**权威源：**

- **业务权限的唯一权威在 Owl-Server**。
- Owl-SFU **不解释业务 RBAC**；只认 Server 签发的 **短期媒体凭证**（如 JWT/会话 token）中声明的能力（例如：可加入 room X、可 publish 音频、是否可 subscribe 等最小集合）。

### 4.3 进房鉴权流（逻辑）

```
客户端 → Server：申请加入语音频道 C
Server：校验 RBAC（VIEW + CONNECT + 可选 SPEAK）
Server：选择 SFU 节点 + 创建/定位 room
Server：签发 media token（短时、绑定 user/guild/channel/room/capabilities）
客户端 → SFU：持 token 建立 WebRTC
SFU：校验 token 与节点密钥/公钥 → 允许发布/订阅
```

权限变更（被踢、被静音、角色变更）时：Server **主动通知 SFU 踢出或改能力**（控制通道），不能只靠客户端自觉。

## 5. Server ↔ SFU：网络与数据路径

### 5.1 目标网络拓扑

- 控制面与 SFU 之间：**内网或公网** 均可部署。
- **音频媒体数据必须客户端 ↔ SFU 点对点（直连路径）**，不经过 Owl-Server 中转 RTP。
- 避免「控制中转节点」拖累带宽与延迟：  
  **Server 只做信令/编排；媒体只走 SFU。**

```
                    ┌─────────────────┐
                    │   Owl-Server    │  控制面：API / WS 信令 / RBAC / 调度
                    │   (控制面)      │
                    └────────┬────────┘
                             │ 控制通道（mTLS / 节点凭证，见第 6 节）
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ Owl-SFU  │  │ Owl-SFU  │  │ Owl-SFU  │
        │  节点 A  │  │  节点 B  │  │  节点 C  │
        └────▲─────┘  └────▲─────┘  └────▲─────┘
             │              │              │
             │    WebRTC 媒体（UDP/ICE）    │
             │              │              │
        ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
        │ Client  │    │ Client  │    │ Client  │
        └─────────┘    └─────────┘    └─────────┘
```

### 5.2 「点对点」含义澄清（本轮共识）

此处 **不是** 客户端之间的 Mesh P2P（千人 Mesh 不可行），而是：

1. **媒体路径上无 Server 中转**（Server 不做 RTP 中继）。
2. 客户端与 **被调度到的 SFU** 建立直连（ICE 打洞 / 公网 IP / 内网直达）。
3. 同频道用户之间由 **该 SFU 转发**，而不是再经第三方中继机房绕路（除非 TURN 兜底）。

TURN 仅作为 NAT 失败时的 **兜底中继**，不作为默认路径；TURN 可独立部署，与 SFU 同机房更佳。

### 5.3 跨节点与调度（后续细化）

| 策略 | 说明 | 定稿 |
|------|------|------|
| 服级节点池 | 创建/配置「服务器」时绑定可用 SFU（含跨境节点） | **必做** |
| 同频道调度 | **一开始即按地域多节点接入**（07） | **必做** |
| **多节点级联** | 池内树/星型转发，禁止全连接 | **必做** |
| **热迁移** | 死亡/Drain/分区/过载(可配)；自动接最近存活节点；允许短暂静音，禁止回大厅手进 | **必做** |

详见 [06-评审定稿决议 §5](./2026-07-20-06-评审定稿决议.md)。

## 6. Server ↔ SFU 控制面认证（防误加 / 防入侵）

### 6.1 威胁模型（本轮关注）

| 威胁 | 风险 |
|------|------|
| 任意进程伪造成 SFU 注册到集群 | 窃听信令、劫持房间、骗取客户端连接 |
| 任意客户端直连 SFU 不经 Server | 绕过 RBAC 偷听/刷流 |
| 公网暴露管理口 | 被扫描利用 |
| 节点被错误手动添加 | 脏节点进入调度池 |

### 6.2 认证体系方向（草案，推荐分层）

**A. 节点身份（Node Identity）**

- 每个 SFU 节点拥有唯一 `node_id` + **长期凭证**（推荐：**mTLS 客户端证书** 或 **节点私钥 + Server 登记的公钥**）。
- **禁止**仅靠「共享一个全局 secret」且长期不变、可复制到任意机器。
- 节点 **首次接入** 需 **预注册 / 审批 / enrollment token（一次性、短时）**，再换成长期证书。

**B. 控制通道（Control Channel）**

- Server ↔ SFU：双向认证（mTLS 或双向 JWT + 证书钉扎）。
- 通道职责示例：
  - 节点注册 / 心跳 / 容量上报
  - 创建/销毁 room
  - 吊销用户会话、强制 disconnect
  - 配置热更新（ICE/TURN 列表等，视需要）
- 管理 API **不默认对公网全开**；公网部署时限制来源 IP + mTLS。

**C. 媒体会话凭证（Media Token）**

- 仅由 **Owl-Server** 签发，SFU 用共享的验证密钥/公钥校验。
- 声明至少：`user_id`、`guild_id`、`channel_id`、`room_id`、`node_id`、`exp`、capabilities（`publish_audio` / `subscribe` 等）。
- **短 TTL** + 可刷新；权限变更立即 **服务端吊销**（SFU 侧会话表 + 控制指令）。

**D. 防错误添加**

- 运维侧：节点加入需 Server 管理接口 **显式 enable** 才进入调度。
- 可选：节点标签（region、内网/公网、租户）+ 调度白名单。

### 6.3 原则一句话

> **SFU 不信任客户端自述权限；只信任 Server 签发的短时 token 与已认证的控制通道指令。**  
> **Server 不信任未知 SFU；只信任已 enrollment 且证书有效的节点。**
