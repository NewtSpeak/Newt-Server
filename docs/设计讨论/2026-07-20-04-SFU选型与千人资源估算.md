## 1. 容量口径（先定定义）

| 术语 | 定义（本项目采用） |
|------|-------------------|
| **节点并发用户** | 已与该 SFU 建立媒体会话、占用 PeerConnection（或等价传输会话）的用户数 |
| **目标** | 单节点 **1000** 并发用户 |
| **非目标（默认）** | 单语音频道内 1000 人 **互相全订音频**（带宽平方级爆炸） |
| **工作负载模型** | 1000 人分布在 **多个语音频道（room）**；单频道建议软上限见下 |

### 1.1 业务限流（**已定稿**，与 SFU 能力解耦）

| 项 | 定稿值 | 说明 |
|----|--------|------|
| 单节点并发 | **1000** | 多子频道分担；调度硬顶（可配置） |
| 单语音频道 | **软上限 50，硬上限 200** | 超软上限进入大房策略；>200 拒绝 |
| 大房形态 | **舞台 + 听讲** | 台上 **软 20 / 硬 50**；协管与抱麦；&gt;50 强制舞台+超额自动禁说（见 07） |
| 小房订阅 | ≤50 可全双工互听 | 实现可优化 |
| 大房订阅 | 听众订 **台上上行（≤50）** | 禁止百人全员互订；客户端可选静音某路 |
| 节点模型 | **同语音频按地域多节点 + 池内级联** | 见 07 专项 1 |
| 上行音频 | Opus **32–48 kbps** 目标 | 可选高质量档 |
| 视频/屏幕 | **后期必做，生态位预留** | 首期可不推流；容量单独系数 |

## 2. 带宽估算模型

### 2.1 符号

- \(N\)：频道内人数  
- \(S\)：每用户订阅的音频流数量（全订时 \(S=N-1\)）  
- \(B_{up}\)：单路上行码率（含 RTP 开销可按 ×1.2）  
- \(B_{down} \approx S \times B_{up}\)：单用户下行  

**SFU 节点总入站（近似）**：\(\sum B_{up}\) ≈ 有发布者人数 × \(B_{up}\)  
**SFU 节点总出站（近似）**：各用户下行之和 ≈ \(\sum_i S_i \times B_{up}\)

### 2.2 场景表（音频 only，\(B_{up}=40\text{kbps}\)，含开销按 48kbps 计）

| 场景 | 结构 | 节点出站粗算 | 评价 |
|------|------|--------------|------|
| A. 20 房 × 50 人，房内全订 | 每房出站 ≈ 50×49×48kbps ≈ **117 Mbps/房**；20 房 ≈ **2.3 Gbps** | 过高，需减订阅或降人数 |
| B. 50 房 × 20 人，房内全订 | 每房 ≈ 20×19×48 ≈ **18 Mbps**；50 房 ≈ **0.9 Gbps** | 千兆网卡吃紧，万兆或降码率更稳 |
| C. 100 房 × 10 人，房内全订 | 每房 ≈ 10×9×48 ≈ **4.3 Mbps**；100 房 ≈ **430 Mbps** | **合理目标区** |
| D. 1000 人 × 各自 1 人房 | 几乎无转发 | 无意义压测 |
| E. 5 房 × 200 人，Top-8 发言订阅 | 每用户下行 ≈ 8×48≈384kbps；200×5×384kbps ≈ **384 Mbps** 量级 | 大房可行路径 |

**结论（架构约束）：**

1. 「1000 并发」必须配合 **多房间分布** 或 **大房 Top-N 订阅**。  
2. 单节点出口建议按 **至少 1–2 Gbps** 网卡规划；生产用 **5–10 Gbps** 更从容。  
3. 内网部署可更大胆；公网按峰值出站计费与 QoS。

### 2.3 入站

1000 人同时说话（极端）入站 ≈ 1000×48kbps ≈ **48 Mbps**，通常远小于出站。  
实际同时说话比例按 10–30% 估即可。

## 3. 内存与 CPU 粗算

### 3.1 量级经验（WebRTC SFU 类，**需压测校准**）

| 资源 | 粗算假设 | 1000 连接量级 |
|------|----------|----------------|
| 每 PeerConnection | 0.5–2 MB（实现差异大） | **0.5–2 GB** 仅连接元数据 |
| 包队列 / jitter 相关 | 每 track 额外 | +0.5–1 GB 可能 |
| 进程与库 | Go/C++ SFU 基线 | 0.2–0.5 GB |
| **内存建议** | 生产单节点 | **8 GB 起，推荐 16 GB**（含余量与突发） |
| CPU | 纯转发、无转码 | **8–16 vCPU** 看包速率与语言实现 |
| 转码 | 默认 **关闭** | 转码会轻易打满 CPU，禁止作为默认路径 |

### 3.2 设计原则（再次强调）

| 原则 | 原因 |
|------|------|
| **不转码** | CPU 与许可复杂度 |
| **不 MCU 混流**（默认） | 与千人目标冲突 |
| **房间=语音频道** | 隔离订阅图 |
| **能力上报调度** | 防单节点过热 |
| **可选 Simulcast 仅视频** | 音频保持单质量档简化 |

## 4. 候选技术栈对比

### 4.1 对比表

| 方案 | 语言/形态 | 优势 | 风险/成本 | 与本项目契合 |
|------|-----------|------|-----------|--------------|
| **mediasoup** | C++ worker + Node/Go/Rust 控制 | 成熟 SFU、管道灵活、生产案例多 | 运维两进程；许可 AGPL 需注意商业 | 强；需评估许可与 Owl 双许可兼容策略 |
| **LiveKit** | Go（SFU）+ 配套 | 开箱房间/权限/多节点；生态全 | 较重；部分能力可能与自研控制面重叠；许可与商业版边界要查 | 中强；易快，但要划清与 Owl-Server 边界 |
| **Pion** 自研 SFU | Go 库 | 与 Go 控制面统一、定制自由、许可友好（MIT） | 工程量大；千人要自研订阅/背压/监控 | 强（长期可控） |
| **ion-sfu / 衍生** | Go + Pion | 比从零快 | 社区活跃度/维护风险 | 中 |
| **Janus** | C 插件 | 老牌 | 架构偏插件单体；与现代编排集成一般 | 弱于前几者 |
| **Jitsi Videobridge** | Java | 会议场景强 | 与 Discord 式多服频道模型不贴 | 弱 |

### 4.2 许可与产品策略提醒

Owl 体系为 **双许可（非商业免费 / 商业付费）**。若 SFU 依赖 **AGPL**（如 mediasoup 默认策略需核对当前版本），商用分发可能被 copyleft 影响。

| 策略 | 说明 |
|------|------|
| A. 自研/Pion MIT | 许可最干净，研发最长 |
| B. 用 AGPL 组件但 **不修改、仅网络服务** | 仍需法务确认；source-available 商业模式要谨慎 |
| C. 购买例外许可 / 选兼容许可栈 | 成本换速度 |

**架构文档级建议（非法律意见）：优先许可友好栈，或 SFU 进程严格隔离并在发布说明中披露依赖。**

### 4.3 选型结论（**已定稿**）

| 项 | 决议 |
|----|------|
| **产品锁定** | **Owl-SFU = Go + Pion 自研** |
| **动机** | 最纯洁许可 + 深度定制（级联、热迁移、舞台、节点池） |
| **不做** | LiveKit / mediasoup 不作为默认媒体内核 |
| **Spike** | 最小进房/转发/token/踢人 → 再压测 1000 与级联原型 |

**一句话：控制面与媒体面均为自研；媒体栈锁定 Pion。**

## 5. 单节点参考规格（规划用）

### 5.1 推荐硬件/云规格（音频为主、模型 C：约 400–800 Mbps 出站）

| 项 | 规格 |
|----|------|
| vCPU | 8–16 |
| 内存 | 16 GB |
| 网络 | **≥ 2 Gbps** 保证带宽（云上选带宽型实例） |
| 磁盘 | 40 GB SSD（日志） |
| OS | Linux；调高 `ulimit -n`、UDP 缓冲 |

### 5.2 进程与端口

| 端口 | 用途 |
|------|------|
| 控制通道 | mTLS gRPC（仅 Server/节点，不对用户） |
| WebRTC UDP 范围 | 按 ICE 配置（如 10000–20000） |
| TURN | **独立** 部署更佳；同机房 |

### 5.3 观测指标（必须）

- 并发 Peer、room 数、每 room 人数  
- 入/出站 bps、丢包、NACK 率  
- CPU、RSS、GC（若 Go）  
- 进房耗时、ICE 失败率  
- 踢人/revoke 延迟

## 6. 压测计划（定稿门槛）

在宣布「支持 1000」前必须完成：

| 步骤 | 内容 | 通过标准（建议） |
|------|------|------------------|
| T1 | 1000 空连接（无媒体） | 内存 < 预算 70%，无 fd 泄漏 |
| T2 | 100 房 × 10 人，全员发包 | 出站与模型误差 < 30%，5 分钟稳定 |
| T3 | 50 房 × 20 人 | 同上；CPU < 75% |
| T4 | 10 房 × 50 人 + Top-8 订阅 | 语音可懂、延迟可接受 |
| T5 | 踢人/revoke 风暴 | 权限撤销 < 1s 生效（P99） |
| T6 | 节点断控信道 | 媒体可短暂维持；重连策略符合信令文档 |

压测工具：自定义 bot（Pion 客户端）或现成 WebRTC 负载工具。

## 7. 调度策略（Server 侧配合）— 对齐 06

| 策略 | 定稿 |
|------|------|
| 服级节点池 | 每 Guild 绑定可用 SFU 集合（含跨境节点）；**仅池内调度** |
| 选节点 | 池内 `ONLINE && enabled && 有容量`；优先 **近 + 低占用** |
| 同频道 | 可多节点 + **级联**；不强制永久单节点 |
| 故障 | **热迁移** 到池内最近且占用最低节点；**不接受**短中断重连体验 |
| Drain | 升级前 DRAINING + 主动热迁 |

## 8. 本轮结论

| # | 结论 |
|---|------|
| 1 | 1000 = **节点并发**（多子频道），不是单房全订 1000 |
| 2 | 单房 **软 50 / 硬 200**；大房 **舞台≤20 发言者 + 听讲** |
| 3 | 带宽出站主瓶颈；规划 **≥2 Gbps**，内存 **16GB** 级 |
| 4 | 默认无转码、无 MCU |
| 5 | **锁定 Go + Pion 自研 Owl-SFU** |
| 6 | **级联 + 热迁移** 为必做（见 06） |
| 7 | 屏幕共享后期必做，容量系数与协议预留 |
| 8 | 「支持 1000」以压测为准；级联场景另增压测项 |
