## 1. 目标与范围

### 1.1 目标

让用户在成员列表、好友列表、资料卡上展示「我在干什么」，对标 Discord 的 Activity 体验，覆盖：

1. **结构化活动（Activity）**：正在玩 / 正在听 / 正在看 / 正在直播 / 竞技中 / 手动自定义活动  
2. **与自定义状态并存**：`custom_text` / `custom_emoji`（心情签名）与 `activities[]`（结构化活动）分层，不互相覆盖  
3. **自动检测（Desktop）**：本机游戏进程检测；可选媒体会话 / Spotify 听歌  
4. **手动设置**：用户可手填「正在玩 X」等，不依赖检测  
5. **隐私可控**：`show_activity_to` 落地；隐身时对外完全隐藏活动  
6. **多端合并**：status / custom / activities 各自规则清晰；服务端权威广播  

### 1.2 产品定位（与 Discord 对齐点 / 差异）

| 点 | Discord | 本文 |
|----|---------|------|
| 在线四态 | online / idle / dnd / invisible | **已实现**，不改语义 |
| 自定义状态 | emoji + 文本 + 过期 | **已实现**（服务端 `CustomStatus`），本专项仅对齐字段与 UI 消费 |
| 活动 | `activities[]`，type 0–5 | **新增**，语义对齐，字段可裁剪 |
| 游戏检测 | 本地进程 + 可更新游戏库 | **Desktop 专用**；Web 仅展示/手填 |
| 音乐 | Spotify 深度集成 + 部分 OS 媒体 | **分里程碑**：先 OS 媒体或 Spotify 二选一，再扩展 |
| Rich Presence RPC | 游戏经本地 IPC 上报详情 | **P2**；首期不兼容 Discord RPC |
| 活动按钮 / 组队 | buttons、party | **P2** 预留字段，首期可不展示 |

## 2. 核心概念

| 术语 | 说明 |
|------|------|
| **Status（在线状态）** | `online` / `idle` / `dnd` / `invisible`；派生 `offline`。会话级上报，多端按优先级合并。 |
| **Custom Status（自定义状态）** | 用户手填的 emoji + 文本 + 可选过期时间。**账号级**（任一端写入覆盖全账号）。对标 Discord Custom Status。 |
| **Activity（活动）** | 结构化「正在干什么」条目：类型、名称、详情、资源图、时间戳等。**按 Gateway 会话上报**，服务端跨端合并后对外展示。 |
| **主活动（Primary Activity）** | 合并后对外优先展示的一条活动（成员列表通常只显示一条）。 |
| **检测源（Source）** | 活动从哪里来：`detected`（进程）、`media`（OS 媒体会话）、`spotify`、`rpc`、`manual`。 |
| **游戏目录（Game Catalog）** | 可执行文件名 → 展示名 / 图标的映射表，供进程检测匹配。 |

**分层原则（A.1）**：

```text
Presence 对外视图 =
  status（点颜色）
  + custom_status?（心情/签名一行）
  + activities[]?（结构化活动，可多条；UI 常只展主活动）
```

三者独立：改活动不清空自定义状态；隐身/离线时后两者对他人一律清空。

## 3. 数据模型

### 3.1 Activity 结构

服务端与 Gateway 载荷统一使用下列 JSON 形状（字段名 snake_case）：

```json
{
  "type": "playing",
  "name": "原神",
  "details": "探索璃月",
  "state": "单人世界",
  "application_id": null,
  "url": null,
  "assets": {
    "large_image": "https://…/cover.png",
    "large_text": "原神",
    "small_image": null,
    "small_text": null
  },
  "timestamps": {
    "start": 1720000000000,
    "end": null
  },
  "party": null,
  "buttons": null,
  "source": "detected",
  "session_id": "可选；仅服务端内部合并用，下发可省略"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `type` | enum | 是 | 见 §3.2 |
| `name` | string | 是 | 主名称，1–128 字符；trim 后非空 |
| `details` | string | 否 | 详情行，≤128 |
| `state` | string | 否 | 状态行，≤128 |
| `application_id` | snowflake/string | 否 | 可选应用目录 ID（RPC / catalog 用） |
| `url` | string | 否 | 仅 `streaming` 建议携带；合法 http(s) URL，≤512 |
| `assets` | object | 否 | 大/小图 URL 或 media proxy key；URL ≤512 |
| `timestamps.start` / `end` | int64 ms | 否 | Unix 毫秒；用于「已进行 1:23:45」或进度条 |
| `party` | object | 否 | P2：`{ id?, size?: [current, max] }` |
| `buttons` | array | 否 | P2：最多 2 个 `{ label, url }` |
| `source` | enum | 是 | `detected` \| `media` \| `spotify` \| `rpc` \| `manual` |
| `session_id` | string | 否 | 上行可省略（服务端以当前 Gateway session 填入）；**下行不发给他人** |

### 3.2 Activity type

| type | 展示前缀（中文 UI） | 典型来源 |
|------|---------------------|----------|
| `playing` | 正在玩 | 游戏进程 / 手动 |
| `listening` | 正在听 | 媒体会话 / Spotify |
| `watching` | 正在看 | 手动 / 未来视频应用 |
| `streaming` | 正在直播 | 手动 URL / 推流工具（后置） |
| `competing` | 竞技中 | 手动 / RPC |
| `custom` | （无前缀，类似自定义活动文案） | 手动；**与 Custom Status 不同**：仍走 activities 结构 |

> **决议 A.2**：`type=custom` 的 activity 与账号级 `custom_text/emoji` **并存不合并**。  
> Custom Status 偏「签名」；`activity.custom` 偏「临时结构化活动」。产品 UI 可弱化 `activity.custom` 入口，仅保留 playing/listening 手填。

### 3.3 Presence 快照 / 事件条目（扩展）

在既有 `snapshot.Presence` / `PRESENCE_UPDATE` 上扩展：

```text
Presence {
  user_id
  status                  -- online|idle|dnd|invisible|offline
  custom_text?            -- 已有
  custom_emoji?
  custom_expires_at?
  activities?             -- 新增：Activity[]；offline 时省略或 []
}
```

| # | 规则 |
|---|------|
| **M.1** | READY 顶层 `presences` 与 `guilds[].presences` 同构，均携带合并后的 `activities`（对观察者已 mask + 隐私过滤）。 |
| **M.2** | 他人视角：`status=offline`（含 invisible 掩码）时 **不得** 出现 `custom_*` 与 `activities`（与现有 custom mask 一致）。 |
| **M.3** | 本人视角：真实 `status`（含 invisible）+ 完整 custom + 完整合并 activities。 |
| **M.4** | 活动数量：上行每 session 最多 **3** 条；合并后对外下发最多 **3** 条；成员列表 UI 默认只渲染 **主活动 1 条**。 |

### 3.4 服务端内存模型（扩展 `presence.userState`）

现有：

```text
userState {
  sessions: map[sessionID] → status
  custom:   CustomStatus      // 账号级
}
```

扩展为：

```text
sessionPresence {
  status:     string
  activities: []Activity      // 该端当前上报；空 = 该端无活动
}

userState {
  sessions: map[sessionID] → sessionPresence
  custom:   CustomStatus      // 账号级，最后写入覆盖（保持现状）
}
```

| # | 规则 |
|---|------|
| **M.5** | 活动 **不落库**（与 status 一致，内存权威）；断线后随 session 生命周期消失。 |
| **M.6** | Custom Status 仍不落库或按现实现；过期惰性判定（已有）。若后续要「重连恢复自定义状态」，由客户端 IDENTIFY 重放（已有路径）。 |
| **M.7** | 游戏目录、用户检测开关等 **偏好** 走 `user_settings` 不透明 JSON 或专用设置键（见 §8）；**不**进 presence 表。 |

### 3.5 隐私字段落地

Server-16 BM.1 中 `show_activity_to` 由占位改为正式字段：

| 字段 | 取值 | 默认 | 说明 |
|------|------|------|------|
| `show_activity_to` | `everyone` / `friends` / `nobody` | **`friends`** | 谁能看到我的 `activities`（不含 status 点本身） |

| # | 规则 |
|---|------|
| **P.1** | `everyone`：与现有 presence 推送受众一致（共同服成员 + 按 16 号规则的好友可见集合）。 |
| **P.2** | `friends`：仅双向好友可见 activities；共同服非好友只看到 status 点（及 custom 是否可见见 P.5）。 |
| **P.3** | `nobody`：对任何他人剥离 activities；本人多端仍可见完整。 |
| **P.4** | `status=invisible` 时 **强制** 对他人剥离 activities 与 custom（压倒 `show_activity_to`）。 |
| **P.5（Custom 可见性）** | 首期 custom 仍跟随 status mask（非 offline 即对共同服可见）；**不**单独吃 `show_activity_to`。若产品后续要「自定义状态也仅好友可见」，另开字段，不塞进本字段。 |
| **P.6** | 修改 `show_activity_to` 后：服务端立即按新规则 **重算并重推** 该用户相关观察者的 `PRESENCE_UPDATE`（或仅推给受众集合变化的用户）；客户端以事件为准。 |

## 4. 多端合并与掩码

### 4.1 Status（沿用）

优先级：`dnd > online > idle > invisible`；无 session → `offline`。  
出处：Owl-Desktop 01 FR-25；`presence.Manager` 已实现。

### 4.2 Custom Status（沿用 + 明确）

| # | 规则 |
|---|------|
| **C.1** | 账号级：任意端 `SetStatusFull` 写入覆盖。 |
| **C.2** | 全部 session 断开 → 清空 custom（与现实现一致）。 |
| **C.3** | 过期惰性清除；载荷带 `custom_expires_at` 供客户端倒计时。 |

### 4.3 Activities 合并

```text
function mergeActivities(sessions):
  pool = flatten(各 session.activities，并打上 session_id)
  // 去重键：type + normalize(name) + source
  // 同键保留 timestamps.start 更早者（或最近更新者，实现选「最近上报」）
  deduped = dedupe(pool)
  // 排序键（主活动优先）：
  //   type_rank: playing=5, streaming=4, listening=3, watching=2, competing=2, custom=1
  //   同 type：有 timestamps.start 的优先；再按 name 稳定排序
  sorted = sort(deduped)
  return sorted[:3]
```

| # | 规则 |
|---|------|
| **A.3** | 合并在服务端完成；客户端只展示下发结果，不做二次跨用户合并。 |
| **A.4** | 某端 Disconnect（resume 窗口结束）后，仅移除该 session 的 activities，重新合并广播。 |
| **A.5** | 同一用户多台电脑各玩不同游戏：可同时出现最多 3 条；主活动取 type_rank 最高。 |
| **A.6** | 手动活动（`source=manual`）与检测活动并存时：manual **不**自动压过 playing 检测；仅按 A.3 排序。产品若希望「手动优先」，可在客户端上报时用单一 manual 并清空 detected（本地策略，见 §7.5）。 |

### 4.4 掩码与推送过滤

```text
对观察者 V 展示用户 U 的 presence：
  1. 取 U 真实合并 status / custom / activities
  2. 若 U.status ∈ {invisible, offline} 且 V ≠ U:
       → status=offline, custom 空, activities=[]
  3. 若 V ≠ U 且 U.show_activity_to 不允许 V:
       → 保留 status/custom（在步骤 2 之后），activities=[]
  4. 下发
```

推送目标集合（与现有 presence 一致，再叠加活动隐私）：

- **他人掩码载荷**：共享至少一个 guild 的在线成员（现 `sharedMembers`）∪ 双向好友（16 号落地后纳入；好友-only 场景无共同服时也需能收 presence——以 16 BS.3 为准）。  
- **activities 字段**：在目标集合上再按 `show_activity_to` 剥离。

| # | 规则 |
|---|------|
| **A.7** | 禁止把「真实 invisible」或「被剥离前的 activities」写入他人载荷（防侧信道）。 |
| **A.8** | 比较前后视图时：`activities` 深度相等则不重复广播（节流）。 |

## 5. Gateway 协议

### 5.1 上行：`op: "PRESENCE"` / `"PRESENCE_UPDATE"`

扩展既有 `presenceUpdateData`：

```json
{
  "op": "PRESENCE",
  "d": {
    "status": "online",
    "custom_text": "考试周",
    "custom_emoji": "📚",
    "custom_expires_at": null,
    "activities": [
      {
        "type": "playing",
        "name": "原神",
        "source": "detected",
        "timestamps": { "start": 1720000000000 }
      }
    ]
  }
}
```

| # | 规则 |
|---|------|
| **G.1** | `status` 非法 → 整帧忽略（与现行为一致）。 |
| **G.2** | `activities` **省略** 表示「本次不修改活动」（保留该 session 旧 activities）。 |
| **G.3** | `activities: []` 表示 **清空** 该 session 活动。 |
| **G.4** | `activities` 非数组 / 单条缺 `type|name|source` / 超限 → 丢弃非法条或整段忽略（实现选：**丢弃非法条，合法条仍写入**；全非法等同清空失败并保留旧值——推荐「合法子集写入」）。 |
| **G.5** | 服务端将 `session_id` 标为当前连接；客户端无需也不应伪造他人 session。 |
| **G.6** | 字段长度超限：截断或拒绝该字段（推荐 **截断字符串** 至上限，避免整帧失败）。 |
| **G.7** | IDENTIFY 可附带与上行同形的初始 `status` + `custom_*` + `activities`，避免先闪无活动再补活动。 |

**部分更新语义小结**：

| 字段 | 省略 | 显式空 |
|------|------|--------|
| `status` | 非法/缺省按实现：现实现要求合法 status；保持「必须带 status」 |
| `custom_text` 等 | 现实现：写入空 custom 会清空；**保持兼容**，客户端应始终带齐 custom 三字段或约定「空字符串=清除」 |
| `activities` | 不改活动 | `[]` 清空活动 |

> **决议 G.8（custom 兼容）**：本专项 **不改变** 现有 custom 上行语义，避免破坏已实现客户端；仅新增 `activities` 的「省略=不改 / []=清空」。

### 5.2 下行：`PRESENCE_UPDATE`

  "t": "PRESENCE_UPDATE",
  "s": 42,
  "d": {
    "user_id": "…",
    "status": "online",
    "custom_text": "考试周",

| # | 规则 |
|---|------|
| **G.9** | 他人载荷永不含 `invisible`；offline 时无 custom/activities。 |
| **G.10** | 对 `show_activity_to` 不允许的观察者：同一事件中 `activities` 为空数组或省略（推荐 **省略或 []**，客户端均视为无活动）。 |
| **G.11** | 本人多端：推真实合并结果（含 invisible + 完整 activities）。 |

### 5.3 READY

`presences[]` / `guilds[].presences[]` 元素与 `PRESENCE_UPDATE.d` 对齐（含 `activities`）。  
好友列表场景的 presence 快照遵循 16 BS.3 + 本文 P.1–P.4。

### 5.4 频控

| # | 规则 |
|---|------|
| **G.12** | 每用户每 session 上行 presence：**建议客户端 ≥ 2s 合并一次变更**；服务端可软限 5 次/10s，超限丢弃并记指标（不踢连接）。 |
| **G.13** | 仅 `timestamps` 推进（听歌进度）**禁止**高频全量广播：客户端对 listening 进度本地推算；服务端仅在 name/details/state/type 变化或 start/end 边界变化时广播。 |

### 6.3 游戏进程检测（M2）

| # | 规则 |
|---|------|
| **D.2** | 轮询间隔默认 **10s**（设置可调 5–30s）；仅当匹配集合变化时上报。 |
| **D.3** | 匹配：规范化可执行文件名（小写、去路径）∈ 游戏目录 `executables[]`。 |
| **D.4** | 命中 → `Activity{ type: playing, name: catalog.name, source: detected, timestamps.start: 首次命中时刻 }`。 |
| **D.5** | 进程消失后 **防抖 5s** 再清除，避免启动器闪烁。 |
| **D.6** | 系统黑名单：浏览器、OwlSpeak 自身、常见 IDE/终端默认不匹配；用户可追加排除列表。 |
| **D.7** | **默认关闭**检测；首次在设置中打开时展示说明文案（扫进程、仅本地匹配、可关）。 |
| **D.8** | 不上传完整进程列表到服务器；只上报匹配后的 Activity 结构化字段。 |

| # | 规则 |

| **D.10** | 用户本地可「登记当前前台应用为游戏」（写入本地 overrides，不强制上传）。 |
| **D.11** | 服务端 catalog 为公共只读数据，无鉴权或任意登录可读；体积保持较小（首期数千条内）。 |

### 6.4 音乐检测（M3）

**路径 A — OS 媒体会话（推荐先做）**

- 读取系统「正在播放」：标题、艺术家、专辑图、时长、进度  
- 映射：`type=listening`, `name=<播放器或固定「音乐」>`, `details=标题`, `state=艺术家`, `assets.large_image=封面`, `timestamps`  
- 暂停超过 **60s** 清除；切歌更新 details（受 G.13 节流）

**路径 B — Spotify OAuth**

- 标准 Authorization Code + refresh；`GET currently-playing`  
- `name="Spotify"`，details/state 为曲名/艺人  

| # | 规则 |
|---|------|
| **D.12** | 音乐检测开关与游戏检测 **独立**；默认均关。 |
| **D.13** | 同时有游戏 + 音乐时，两条都可上报；主活动按服务端 type_rank（playing > listening）。 |
| **D.14** | 首期实现 **至少一条** 音乐路径（A 或 B）；另一条可紧随。 |

### 6.5 手动活动与本地策略

| # | 规则 |
|---|------|
| **D.15** | UI 提供：清除活动 / 手动「正在玩」/「正在听」（name 必填）。 |
| **D.16** | 手动设置时：本地 Aggregator 进入 `manual_override` 模式——**暂停**用检测结果覆盖手动项，直到用户「恢复自动」或清除手动。 |
| **D.17** | 自动模式下：检测结果写入 `activities`；无检测则 `[]` 或省略策略与 G.2/G.3 一致（无活动时定期 `[]` 仅在从有到无时发一次）。 |

## 8. REST API（补充）

| 方法 | 路径 | 说明 | 优先级 |
|------|------|------|--------|
| 已有 | `GET/PATCH /users/@me/privacy` | 增加读写 `show_activity_to` | M1 |
| 可选 | `GET /api/v1/activity/game-catalog` | 公共游戏目录，支持 `If-None-Match` | M2 |
| 可选 | `POST /api/v1/activity/spotify/oauth/*` | Spotify 连接（若选路径 B） | M3 |

**不提供**「查询任意用户当前活动」的独立 REST：一律走 Gateway presence 缓存；资料卡打开时用本地 store，缺失可依赖近期 `PRESENCE_UPDATE` 或成员列表订阅（大服懒加载成员时 presence 随订阅补齐，与 14 FR-11 一致）。

## 9. 服务端实现要点

| 模块 | 变更 |
|------|------|
| `internal/presence` | `sessionPresence`；`SetStatusFull` 增加 activities 参数或新方法 `SetActivities`；`Info` / mask / merge / equal；广播 payload 填 `Activities` |

## 10. 里程碑

### M1 — 协议 + 手动活动 + 展示 + 隐私（P0）

- [ ] Gateway 上/下行与 READY 扩展 `activities`  
- [ ] `presence.Manager` 按 session 存储与合并、mask、相等性节流  
- [ ] `show_activity_to` 正式落地（默认 `friends`）  
- [ ] Desktop：手填/清除活动；成员列表、资料卡、左下角展示  
- [ ] Web：同展示 + 手填  
- [ ] 隐身 / 离线掩码测试  

**验收**：A 手填「正在玩 X」，好友 B 2s 内可见；A 隐身后 B 看不到活动；A 设 `nobody` 后好友也看不到活动但可见在线点（非隐身时）。

### M2 — 游戏进程检测（P0/P1）

- [ ] Tauri 进程扫描 command  
- [ ] 内置 catalog + 可选远端 catalog  
- [ ] 开关默认关、排除列表、防抖  
- [ ] Aggregator 节流上报  

**验收**：启动目录内游戏后 ≤15s 出现「正在玩」；退出后 ≤15s 清除；未授权检测时无活动。

### M3 — 音乐（P1）

- [ ] OS 媒体 **或** Spotify 其一  
- [ ] `listening` 展示与进度策略（G.13）  

**验收**：播放/暂停/切歌状态正确；与游戏并存时主活动为游戏。

### M4 — 增强（P2）

- [ ] 完整 assets / 进度条打磨  
- [ ] Owl RPC 或 Discord RPC 兼容评估  
- [ ] `streaming` / `buttons` / `party`  
- [ ] 用户本地「登记为游戏」同步策略
